## 一、项目是什么

一个常驻 daemon（macOS launchd 托管），通过飞书事件订阅（`lark-cli event consume` WebSocket 长连接）实时监听「Chatbot badcase 收集跟进群」的消息，自动完成两件事：

1. **badcase 自动分析**：群里有人发带日志ID/trace的消息 → 自动抽 ID → 查 trace → 解密（全自动 @板栗 BPM 工单）→ LLM 根因分析 → bot 自动回复结论到 thread
2. **autofix 自动修复**：分析出结论后（或在已有结论帖下回复触发词），自动独立复核 → 评估复杂度 → 对简单可改的给出修改计划 → 等刘昕明审批 → zcode headless 全自动改码+提 MR → 把 MR 链接发回群里

**核心特点**：分析阶段后台化（不阻塞监听）、worktree 隔离（基于 develop 最新改码）、审批人在群里回复关键词推进。

## 二、架构与运行方式

### 2.1 部署
- launchd job：`com.xinming.badcase-event-monitor`
- plist：`~/Library/LaunchAgents/com.xinming.badcase-event-monitor.plist`（`KeepAlive=true` + `RunAtLoad=true`，崩溃/退出立即重启）
- 管理命令：
  ```bash
  launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.xinming.badcase-event-monitor.plist  # 启动
  launchctl bootout gui/$(id -u)/com.xinming.badcase-event-monitor                                  # 停止
  launchctl kickstart -k gui/$(id -u)/com.xinming.badcase-event-monitor                             # 重启
  tail -f ~/.badcase_event_state/monitor.log                                                        # 看日志
  ```

### 2.2 单进程，多模块
**只有一个进程**（`badcase_event_monitor.sh`），autofix 是其中的模块，不是独立进程。进程结构：
```
主进程（拿单实例锁）
├─ consume 子进程（lark-cli event consume，WebSocket 长连接，stdout→FIFO）
├─ 主循环：read FIFO → process_event → （派活后台分析/检测审批/检测触发词）
├─ 后台分析子进程 N（run_analysis_background，≤ MAX_CONCURRENT_ANALYSIS=3 并行）
│   └─ analyze_one_log_id → resolve_trace_ids → fetch_and_check_decrypt → run_zcode_session → 结论帖
│       └─ autofix_on_conclusion_posted → ( autofix_run_review ) & 后台
└─ 后台 review/execute 子进程（autofix，由审批/触发推进）
```

### 2.3 状态目录 `~/.badcase_event_state/`
| 路径 | 用途 |
|---|---|
| `events.fifo` | consume → 主循环 的命名管道 |
| `badcase_event_monitor.pid` | 单实例锁（shlock） |
| `processed_events.txt` | message_id 幂等账本 |
| `analyzed_logids.txt` | 已分析的日志ID/trace 去重账本（防重复回复） |
| `autofix_tasks/task_*.json` | autofix 任务持久化（状态机） |
| `autofix_processed_conclusions.txt` | 结论帖幂等账本 |
| `analysis_tasks/task_*.json` | 后台分析任务持久化（供 kill 后恢复） |
| `analysis_pids/*.pid` | 后台分析进程 pid（并发计数+zombie回收） |
| `traces/trace_<trace_id>/` | trace 缓存（trace_details.json / span_summary.tsv / metadata.json） |
| `monitor.log` | 主日志 |
| `launchd.err.log` / `launchd.out.log` | launchd 捕获的 stderr/stdout |

### 2.4 敏感配置
`~/.badcase_event_env`（chmod 600，**不提交 git**）：
- `ANTHROPIC_API_KEY`（bigmodel API key）
- 可选覆盖 `AUTOFIX_REVIEWER_OPEN_ID`（审批人 open_id，留空则启动时从 `lark-cli auth status` 自动取本机登录者）

## 三、关键流程

### 3.1 分析流程（process_event → analyze_one_log_id）
```
消息进 FIFO
→ process_event:
   1. message_id 幂等（processed_events.txt）
   2. autofix_check_approval_reply（审批检测：刘昕明在 awaiting 任务 thread 回复同意/反对）
   3. autofix_check_conclusion_trigger（结论触发：刘昕明回复 autofix/修一下，基于结论帖建任务）
   4. 跳过 bot 自己发的
   5. extract_log_ids（抽日志ID/trace，排除 uid/fornax space-id）
   6. analyzed_logids.txt 去重过滤（已分析的跳过）
   7. mark_processed + analysis_task_write（持久化）
   8. 并发控制（≤3）→ run_analysis_background 后台派活
→ analyze_one_log_id（后台子进程内）:
   resolve_trace_ids（时间锚点定位窗口，6h→72h→168h 渐进；StepID 纠错）
   → fetch_and_check_decrypt（抓 trace，未解密走 BPM 工单 @板栗）
   → run_zcode_session（多轮证据驱动 LLM 分析：preliminary→CANDIDATE_SPAN_IDS→证据包→深度复核）
   → reply_thread_and_mark（发结论帖）
   → mark_logid_analyzed（记去重账本：原始ID+纠错后RunLogID+trace 全记）
   → autofix_on_conclusion_posted（触发 autofix review）
```

### 3.2 autofix 状态机
```
[reviewing] autofix_run_review
   ├─ zcode 独立复核结论（在 develop 最新 worktree 读代码验证）
   ├─ 判 MANUAL（>3文件/涉外部库/平台prompt非代码）→ finalize_manual 回复转人工，END
   └─ 判 SIMPLE_AUTO → 发修改计划帖到 thread → [awaiting_approval]
[awaiting_approval] 等刘昕明回复（autofix_check_approval_reply 检测）
   ├─ 同意词（同意/可以/赞同/批准/LGTM/改吧）→ [executing]
   ├─ 反对词（不同意/别改/等等）→ 中止，END
   ├─ 其他人讨论 → 记入 discussion_context（执行时遵循）
   └─ 72h 超时 → 挂起，END
[executing] autofix_execute
   zcode headless 全自动：worktree(develop最新) → 切fix分支 → 改 → gofmt → commit → push → 建MR
   → 发 MR 链接回 thread @review → [done]
```

### 3.3 结论触发（autofix_check_conclusion_trigger）
覆盖「bot 自发消息事件订阅收不到」的场景：刘昕明在任意结论帖 thread 回复触发词（`autofix`/`自动修复`/`修一下`/`fix一下`），基于该 thread 根消息的结论建任务跑 review。

## 七、已知问题与优化方向（给下一个 Agent）

### 7.1 性能
- **trace 查询慢**：查不到 trace 的 case 会跑满 6h→72h→168h 三级窗口 + StepID 纠错，单条可能 15-30 分钟。3个ID串行更慢。优化方向：并行查多ID；查不到的ID快速失败（如 6h+72h 都空就直接放弃，不等168h）。
- **日志重复打印**：每条 log 被 tee 写两次（monitor.log + launchd.err.log 同时捕获 stderr）。不影响功能但日志膨胀。原因：`log()` 用 `tee -a` 写 stderr，而 plist 又把 stderr 重定向到 launchd.err.log。

### 7.2 健壮性
- **zcode 限流/网络故障**：bigmodel 限流时 zcode 8 轮重试，单 case 可能空转十几分钟。可考虑全局令牌桶限速。
- **飞书 token 获取超时**：偶发 `resolve tenant access token ... context deadline exceeded`（网络问题），导致回复发送失败。已有重试但未必够。
- **事件订阅不推 bot 自发消息**：飞书固有行为，已用「结论触发词」方案覆盖（用户在 bot 帖下回复 autofix）。

### 7.3 功能增强方向
- **结论触发的讨论上下文**：当前结论触发建任务时没把 thread 内既有讨论纳入 discussion_context，可在建任务时拉 thread 全部回复作为上下文。
- **去重账本过期清理**：analyzed_logids.txt 只增不减，长期会膨胀。可加 TTL（如30天前的清理）。
- **autofix 失败重试**：execute 失败后任务变 failed，需手动重置才能重跑。可加自动重试（有限次）。
- **并发分析的 trace 解密竞争**：多条同时等板栗解密，可排队避免压垮审批人。

### 7.4 代码质量
- 主脚本 1941 行偏大，可考虑拆分（分析模块 / autofix 模块 / 工具函数 分文件）。
- 缺少 shellcheck CI（本机未装 shellcheck，多次 `set -u` 下的 unbound/local 问题靠运行时发现）。
- `run_zcode_session` 是 `()` 子 shell 定义，其 cleanup 函数经 trap 调用时访问 local 变量需 `${var:-}` 兜底（已修，但模式脆弱）。

## 八、重要约定与踩过的坑

1. **绝不用 `kill -9` 关 consume**：会泄露服务端 OAPI 订阅（重启报 "subscription already exists"）。用 SIGTERM。
2. **`--once`/`--once-autofix` 不经单实例锁**：可与常驻 daemon 同时运行，补跑/调试无需停 daemon。
3. **worktree 的 git stdout 必须重定向**：`ensure_autofix_worktree` 里 git 命令用 `>>log 2>&1`，否则 "branch set up to track" 提示污染函数返回值，zcode 拿到垃圾 cwd。
4. **审批判定同意优先**：「可以，不要枚举」这类句中带局部否定的同意，必须先判同意意图，避免被"不要"误判反对。
5. **thread_id（omt_）判断归属**：话题群回复 mget 不返回 root_id/parent_id，只有 thread_id。
6. **BASHPID 而非 $$**：子 shell 里 `$$` 是父 pid，要用 `$BASHPID`（且 `${BASHPID:-$$}` 兜底）。
7. **顶层不能用 local**：脚本非函数区域（如启动恢复段）禁用 `local` 关键字。
8. **去重记录全部关联ID**：StepID/RunLogID/trace 都要记，否则同case不同ID表达会重复分析。
9. **Fornax URL 的 space ID 要排除**：`fornax.../space/<id>/...` 的 id 是空间ID不是日志ID。
